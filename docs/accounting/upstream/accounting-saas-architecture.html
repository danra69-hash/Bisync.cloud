Four planes

The control plane holds no financial data. The compliance plane holds no business logic that isn’t country-specific. Everything between the subledgers and the ledger core passes through one rule engine, and nothing except the ledger core may write a journal line.

Ledger core — entity relationships

The wide journal_line with dimensions denormalised onto it is the single most important schema decision for reporting. Reports must never join through documents to find a cost centre.

The invariants, enforced in the database

-- DELETE is included deliberately: without it, deleting a line from an unposted
-- journal in a later transaction leaves it permanently unbalanced, silently.
CREATE CONSTRAINT TRIGGER journal_balanced
  AFTER INSERT OR UPDATE OR DELETE ON journal_line
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION assert_journal_balanced();

-- TWO invariants, both required:
--   (a) per transaction currency:  GROUP BY txn_currency, SUM(±txn_amount) = 0
--   (b) whole journal, functional:                        SUM(±func_amount) = 0
-- Grouping by func_currency would be a no-op — it is constant per entity.
-- Caveats: a zero-line journal never fires a FOR EACH ROW trigger (check at post),
-- and constraint triggers cannot be FOR EACH STATEMENT (N lines = N aggregates).
Also enforced in the DB
1Reject UPDATE/DELETE on lines where posted_at IS NOT NULL
2Reject inserts whose effective_date lands in a closed period
3Line currency must be permitted for its account; func_currency = entity’s functional currency
4Hash chain per (tenant, series, fiscal year) — makes immutability demonstrable to an auditor
5Every unique index and FK is tenant-scoped (constraints bypass RLS by design)
Money representation
·Integer minor units (bigint) + explicit ISO 4217 currency. Never floats, never Postgres money
·0-decimal (JPY, KRW, VND), 3-decimal (KWD, BHD, OMR) currencies are real — carry minor_unit in a currency table
·Decimal for quantities, unit prices, tax rates, FX rates. Rates at numeric(20,10) with explicit direction
·Round once, last, with an explicit mode — Python defaults to ROUND_HALF_EVEN, which surprises accountants
·Allocation must be exhaustive — never round(total/n) per part. Fowler’s allocate() and largest-remainder give the same total but different distributions; pick one and use it everywhere

Four layers of isolation

RLS is the right second layer, not the only one. It turns an application bug into zero rows instead of a breach — but it fails silently, so the application layer must fail loudly.

The three things most likely to bite you

FailureSymptomFix
Plain SET instead of transaction-scoped set_config breach Under PgBouncer transaction pooling the connection is handed to the next client at COMMIT — tenant A’s context becomes tenant B’s set_config('app.tenant_id', :tid, true) inside an explicit transaction. It also takes a bind parameter, which SET LOCAL cannot
Missing NULLIF on the GUC 3am page Zero rows on cold backends, 500s on recycled ones — ''::uuid raises, and an unset GUC is NULL only until the session has ever defined it NULLIF(current_setting('app.tenant_id', true), '')::uuid — normalises both cases to NULL, fails closed consistently
Cross-tenant cached plan reuse 3am page Nondeterministic latency — a plan built while a whale was current gets reused by a small tenant (orders of magnitude slower) and vice versa (row estimate off by 10⁴ → nested loop over 600k rows) ALTER ROLE app_rw SET plan_cache_mode='force_custom_plan', and disable client statement caching. Note this does not rescue parameterless prepared statements
RESTRICTIVE policy with only one permissive policy silent Restrictive policies only subtract. A role with no permissive policy of its own — app_reports, or the owner under FORCE — sees zero rows on every table. Reports come back empty and RunPython data migrations silently no-op One permissive policy per role that needs access; maintenance paths use SET row_security = off, which errors rather than truncating. The “≥1 policy exists” CI gate passes this — assert reachability per role

The enabling piece is a tenant_routing table consulted at connection acquisition, built in Phase 0 even while there is one cluster. Roughly 50 lines. Retrofitting it means touching every connection site in the codebase. Note that row-filtered logical replication does not copy sequences — reset the document counters on the target before cutover or invoice numbering collides.

Explicitly rejected

Schema-per-tenant

Catalog bloat degrades the planner past a few hundred tenants; migrations serialise per schema (a 30-second migration × 800 tenants = 6.5 hours of deploy with an inconsistent schema throughout); and search_path provides no database-level enforcement — a wrong path is a full cross-tenant read with no backstop.

TigerBeetle as the GL

Excellent and Jepsen-verified, but a data plane for high-volume transfers — fixed 128-byte records, no strings, no ad-hoc query. An accounting posting path is drenched in metadata lookups. Revisit only for a high-volume money-movement subledger, with Postgres remaining the GL.

Event sourcing over a message broker

Buys replay and derived views; costs transactional cross-aggregate invariants — and Σdr = Σcr is exactly such an invariant. Use event-sourcing-shaped storage inside one ACID database instead.

ClickHouse at seed stage

Warranted only for cross-tenant, always-on, sub-second dashboards over billions of rows. For a ledger product, primary Postgres → read replica → DuckDB over per-tenant Parquet is where you should stop.

Open questions

1Which three countries first? The pack abstraction needs three genuinely different regimes to be proven — suggest France (PDP + FEC + PCG), Germany (decentralised, no central platform) and Malaysia or Singapore (Peppol 5-corner).
2Who is the buyer? SMB self-serve, mid-market with an in-house accountant, or accounting practices managing many client books? Practice management changes the identity model and the entire UX.
3Does v1 include inventory? Costing is roughly a quarter of engineering on its own.
4Is money movement in scope, or integrate-and-reconcile only? This is the TigerBeetle decision and the licensing question behind it.
5Migration from Xero / QuickBooks / Sage / Tally? Often the actual sales blocker, and it constrains the COA model.
6Target scale in 24 months — 500 tenants or 50,000? Above ~2,000, partitioning and promotion tooling move from Phase 3 into Phase 1.
